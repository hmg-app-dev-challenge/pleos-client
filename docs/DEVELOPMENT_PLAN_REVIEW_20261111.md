# 차Park 개발 계획 전면 재검토안

작성일: 2026-11-11 · 기준안: 「차Park 통합 기획안_20261111」 · 팀 차박차박

개정: v1.1 · 「PLEOS_CAMPING_SDK_DEVELOPER_GUIDE.md」 및 공식 SDK 사용 신청·릴리스·Capability·내비 권한 문서 대조 반영.

## 1. 재검토 결론과 근거 수준

차Park의 제출용 프로토타입을 **차량에서 시작하고 끝나는 단일 Pleos 앱**으로 재정의한다. 사용자가 정차 중 현재 위치·배터리와 장소 조건을 비교하고, 필요한 준비 행동을 확인한 뒤 내비게이션과 수면 준비로 이어지는 경험을 구현한다.

이 문서는 기존 개발 계획과 디자인 보강안의 범위·일정을 대체한다. 통합 기획안의 방향을 기준으로 삼되, 그 안의 제안·가설을 검증된 사실로 승격하지 않는다. 첨부 문서의 인터뷰·운영처 문의·제출 지시는 이번 검토에서 실행할 외부 행동으로 해석하지 않았다.

- **이번에 확인:** 작업 폴더는 비어 있으며 기존 코드·의존성·빌드 환경은 없다. 따라서 코드 마이그레이션이 아니라 신규 프로젝트 계획이다.
- **공식 문서 재확인:** SDK 모듈 구성, Capability·권한 정책, 위치 조회의 한계, 내비게이션 연동 개념, 1차 제출물 구분.
- **앞선 Figma 조회로 확인:** Foundations의 Asta Sans·Light/Dark 토큰, Components의 버튼·제목·선택·팝업 등. 완성된 차Park 화면이나 Android UI 라이브러리가 제공된 것으로 보지 않는다.
- **이 문서의 구현 기본값:** 로컬 우선 구조, 화면·규칙 우선순위, 데모 임계값, 일정 관문. 실제 SDK 시험이나 사용자 검증 결과가 아니다.
- **미실시:** SDK 실행, APK 빌드, 장소 3곳의 개별 검증, 인터뷰, 사용자 테스트, 디자인 화면 제작.

첨부 개발자 가이드는 이전 「차박 한곳」 휴대폰·서버 연동 기획의 기술 검토 자료다. 제품 범위는 최신 통합 기획안을 우선하고, SDK 계약·제약만 선별 반영한다. 문·창문 조회, ICE/하이브리드 확장, 외부 앱 공유, 음성·기록 기능을 이 문서의 P0로 자동 추가하지 않는다.

**가장 중요한 수정:** 위치 자동 조회와 수면 직접 제어는 프로젝트 사용 가능 상태를 확인한 경우에만 활성화한다. P0는 SOC·목적지 전달·조건 판단·수면 안내를 중심으로 검증한다. 해당 기능의 SDK 문서가 공개됐다는 사실만으로 우리 프로젝트에서 사용할 수 있다고 보지 않는다.

성공 기준은 기능 개수가 아니라 **같은 장소에서 배터리 변경 → 충전 행동 변경**, **장소 변경 → 식사·현장 확인 변경**, **계획 → 실제 내비 요청**, **지원 여부 → 설정 요청/안내 구분**이 한 흐름으로 보이는 것이다.

| 경로 기반 판단과 도착 잔량 불확실성 | P0 배터리 규칙은 현재 SOC만 사용. 경로가 없으면 도착 SOC·주행거리·주행시간을 생성하지 않음 |
| 4일 개발 계획과 11/15 마감 | 11/11~14 개발·검증, 11/15 제출 버퍼. 11/11은 남은 시간만 사용하며 미완료 관문을 명시 |

## 4. 구현 범위와 순서

### P0 — 제출 프로토타입

1. 플랫폼 조작 제한 확인, 현재 SOC 조회. 위치 자동 조회는 사용 가능 상태 확인 후 활성화하며, 불가 시 선택 지역/거리 없는 목록 또는 명시적 데모 위치로 진행.
2. 인원(1/2인), 식사(조리된 식사/현장 조리), 반려동물 유무, 보유 장비를 짧은 선택으로 입력.
3. 서울·수도권 장소 3곳의 근거 있는 비교. 항상 최대 3곳을 보여주며 후보 부족 시 실제 개수만 표시.
4. 장소·차량·사용자 조건으로 출발 전 행동/현장 확인/준비물 생성. 변화 이유 표시.
5. 목적지 내비 요청과 성공·실패 처리. 경유지는 지원 확인 시 전달하고, 미지원이면 제안까지만 제공.
6. 도착 확인 뒤 허용된 정차형 화면에서 수면 준비 안내. 직접 제어는 프로젝트 사용 가능 상태·승인·Capability·신뢰 가능한 주차 상태를 모두 확인한 경우에만 사용자 확인 후 요청.
7. 변경 설정과 수동 철수 안내를 보여주고 여행을 종료. 자동 복원으로 표현하지 않음.

### P1 — P0 검수 통과 이후

우선순위: 변경 설정 자동 복원 → 이전 조건 재사용 → 준비 요약 TTS → 빠뜨린 장비 기록. 장소 신고·지원 범위 확대는 제출 후로 둔다. P1이 미완성이면 영상과 지원서에서 구현 완료로 쓰지 않는다.

자동 복원은 직접 제어가 실제로 활성화된 경우에만 착수한다. 직접 제어가 비활성인 제출 구성에서는 이전 조건 재사용부터 진행한다. Door/Window 조회는 P0 완료 뒤 검토할 선택 확장이며, 지원 영역·원시 상태값을 검증하기 전에는 수동 확인을 유지한다. TTS도 프로젝트 사용 가능 상태 확인이 선행된다.

### 이번 제출 개발에서 제외

휴대폰·QR·계정·Firebase 동기화·서버 운영, 지도 탐색 UI, 전국 검색, 다중 필터, 휴식/독서/커스텀 모드, 시트 제어, 예약·결제·커뮤니티·AI, 냉난방 지속 시간·귀가 가능성 계산, V2L·유틸리티 모드 직접 실행, 전원 종료 후 감시.

장소 상세와 출처는 S3의 하위 상세 패널에서 읽는다. 웹 브라우저 연결을 필수로 만들지 않고 출처 제목·URL·확인일을 앱 안에서 볼 수 있게 한다. 실제 좌표로 기본 내비에 전달하며 앱 내 지도 렌더링은 만들지 않는다.

### 시각 명세

- 원본: [Foundations](https://www.figma.com/design/zHQP956O40m7ra3Bobyr4H/Pleos-App-Market-Design-System?node-id=7-2), [Components](https://www.figma.com/design/zHQP956O40m7ra3Bobyr4H/Pleos-App-Market-Design-System?node-id=7-3).
- Asta Sans: 제목 Title/Large/Strong 40/52, 버튼 Title/Small/Strong 32/40, 본문 Body/Medium/Normal 28/36, 보조 Body/Small/Normal 26/34, 라벨 Label/Medium 24/28. 숫자는 확인한 크기/행간이며 Android sp에 대응한다.
- Light/Dark의 background/surface/text/button/divider 의미별 토큰을 사용한다. 확인한 Light background/primary는 #F7F8FA, text/dark/primary는 #131417이다. Dark는 원본 값으로 대응하며 임의 반전하지 않는다.
- 주요 버튼 Large 높이 100을 기본으로 한다. 확인한 Large Primary는 최소 너비 140, 좌우 패딩 40, 상하 패딩 16, 반경 32이다. 원본 치수는 실제 앱 밀도·창 크기를 대조하여 dp에 대응하고 화면 전체 축소로 맞추지 않는다.
- ivi_title Main/Depth를 사용하고 Radio/Phone/Music용 ivi_header는 사용하지 않는다. 차Park 기능과 무관한 예제 메뉴·아이콘을 복사하지 않는다.
- 버튼 Enabled/Pressed/Disabled, 선택 상태, 로딩 상태를 구현한다. 성공·제한·미확인은 색상과 문구를 함께 쓴다.
- 가로는 요약+내용의 2열, 좁은 창은 세로 1열로 재배치한다. 가용 폭이 두 패널의 최소 폭을 충족하는지 기준으로 전환하며 물리 기기의 회전만으로 판별하지 않는다.
- form_factor의 구체적 값과 에뮬레이터 화면 규격은 미확인이다. 1일차 측정값과 Figma 변수를 대조하여 공통 레이아웃 상수로 고정하고 README에 기록한다.
- 정차 중에도 긴 텍스트 입력을 요구하지 않는다. 숫자·선택 컨트롤 위주로 구성하고, 장비 추가 자유 입력은 제외한다.

공식 가이드는 짧은 시간에 읽히는 정보와 지연 시 진행 상태 표시를 요구한다. 입력 피드백은 0.25초 이내 나타나도록 하고, 테마별 주요 글자·아이콘 대비를 검수한다. [Pleos UI Design Guide](https://document.pleos.ai/docs/connect/guide/docs-design/Introduction/intro)

## 6. 기술 구조와 데이터 계약

### 최소 구현 구조

**Kotlin + Jetpack Compose 단일 Android 앱**을 구현 기본값으로 선택한다. SDK 연동은 UI와 분리한다. 공식 릴리스에서 확인한 Vehicle 2.3.2·NaviHelper 3.0.5를 최초 검증 대상으로 고정한다. FusedLocation 1.1.3·TTS 3.3.1은 사용 가능 상태를 확인한 뒤 추가하고 STT는 이번 범위에서 제외한다. [SDK 릴리스 노트](https://document.pleos.ai/docs/pleos-only/release-note/sdk-release-note)

첨부 가이드의 설치 기준은 minSdk 28 이상·Gradle 8.0 이상·Emulator 2.1.0/API 34이다. 이는 검증 출발점이며 로컬 빌드 성공 기록은 아니다. AGP·JDK·Kotlin·Compose·compileSdk·targetSdk는 1일차 공식 샘플과 배포 조건을 대조해 호환 조합을 고정한다. API 34 시스템 이미지와 minSdk를 혼동하지 않는다.

흐름: `Compose 화면 → ViewModel/StateFlow → 순수 판단 규칙 + Repository → Pleos 어댑터 또는 로컬 데이터`.

- 단일 앱 모듈 안에 ui/domain/data/pleos 패키지를 둔다. 제출 전 다중 Gradle 모듈화는 하지 않는다.
- 장소·규칙은 버전이 있는 앱 내 JSON, 활성 여행·제어 기록은 DataStore에 저장한다.
- Room·Firestore·로그인·백엔드 API는 도입하지 않는다. 서버 담당은 데이터·규칙·검증 담당으로 전환한다.
- SDK 객체는 초기화/구독/해제를 관리하고 화면 재생성 때 리스너가 중복 등록되지 않게 한다.
- 실연동 실패 시 자동으로 mock으로 바꾸지 않는다. 사용자에게 실패를 알리고 데모 모드 선택 시에만 예제 값을 사용한다.

## 7. 장소 후보와 판단 규칙

### 장소 확보 및 순서

1. 데이터 담당이 서울·수도권 후보 3곳의 공식 운영 자료로 숙박·주차·운영 시간 등 핵심 필드를 확인한다. 실제 장소는 이번 검토에서 확정하지 않았다.
2. 명시적 차내 숙박 금지는 차박 후보에서 제외한다. 주차 허용만 확인된 장소는 숙박 허용으로 표시하지 않는다.
3. 숙박 허용 근거가 있는 후보를 우선하고, 숙박 미확인 후보는 별도 '확인 필요' 그룹으로 낮춰 보여준다. 미확인 후보를 검증된 숙박 장소로 세지 않는다.
4. 각 그룹 안에서는 현재 위치 기준 직선거리순으로 최대 3곳을 보여준다. 직선거리라고 명시하고 도로 거리·소요 시간으로 표현하지 않는다. 동률은 장소 ID로 고정한다.
5. 위치를 얻지 못하면 거리 순위 없이 고정 목록과 '거리 미확인'을 표시한다. 배터리는 후보 카드의 충전 검토 상태와 선택 후 행동에 반영하며, 검증되지 않은 도착 가능 점수로 순위를 바꾸지 않는다.
6. 실제 조건으로 비교 장면이 구성되지 않으면 별도의 가상 fixture로 규칙만 시연한다. 실장소 데이터와 가상 시나리오를 섞어 '검증 장소 3곳' 조건을 충족했다고 주장하지 않는다.

근거의 확인일은 자료 게시일과 구분한다. 확인일이 있다는 이유만으로 정보를 최신이라고 보장하지 않는다. 상충 자료나 유효기간이 끝난 안내는 unknown으로 처리하고 출처를 함께 보여준다.

### P0 규칙

| ID | 조건 | 결과 |
| --- | --- | --- |
| B1 | 현재 SOC 35% 미만 | 출발 전 '충전 경유 검토' 추가. 35%는 팀 데모 기본값이며 주행·숙박 가능 기준이 아님 |

규칙은 제한/불확실성 안내를 일반 준비 제안보다 먼저 정렬하고 ID로 중복 제거한다. SDK의 SOC 반환 타입·단위·스케일을 AAR/공식 명세로 확인한 뒤 백분율로 정규화하고, 정규화 값에만 0~100 범위와 35% 규칙을 적용한다. 원시값을 곧바로 %로 읽거나 0~100으로 잘라내지 않는다. 35% 경계, 미수신, 조건 충돌을 테스트한다. 이전의 30/20·50/35 3단계와 전비·용량 기반 도착 SOC 추정식은 사용하지 않는다.

## 8. SDK 검증과 상태 처리

공식 SDK에는 Vehicle·NaviHelper·FusedLocation 등이 있고, Vehicle 사용에는 Capability와 승인된 권한 범위 확인이 필요하다. 문서에 모듈이 있다는 사실과 팀 환경에서 실제 호출되는 것은 별개다. [SDK Overview](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/)

공식 신청 안내는 Vehicle State·NaviHelper를 신청 없이 사용 가능, FusedLocation·TTS·STT·Vehicle Control을 준비 중으로 설명한다. 팀의 로그인된 My Project 상태는 이번에 확인하지 않았다. 첫 관문은 코드 작성보다 **프로젝트별 기능 상태 확인**이다. 준비 중/미승인 기능은 의존성·권한·실제 호출을 기본 빌드에 추가하지 않고 안내/수동/데모 경로를 사용한다. Vehicle State의 사용 가능 안내도 배포 시 개별 권한 심사와 동일하지 않다. [프로젝트 생성 및 SDK 사용 신청](https://document.pleos.ai/docs/pleos-only/create-my-project)

| 항목 | 1일차 검증 | 구현 성공 조건 | 실패 시 제출용 처리 |
| --- | --- | --- | --- |
| 위치(조건부) | 프로젝트 사용 상태부터 확인, 가능할 때 지원·권한·마지막 위치·업데이트·시각 | 관측값으로 후보 거리 변화; 기본 P0 완료와 별도 평가 | 선택 지역/거리 없는 목록 또는 명시적 데모 위치 |
| 배터리 | 현재 SOC 조회·갱신 | Virtual Console 변경이 판단에 반영 | 실패 상태, 선택한 데모 SOC로 규칙만 시연 |
| 주행 제한·주차 | UX 제한 상태·별도 주차 신호·연결 해제 | UX 제한/불명은 상세 조작 차단, 주차 불명은 직접 제어 차단 | 실제 제어 차단, 데모 토글은 시뮬레이션 전용 |

| 경유지 | 목적지 유지·충전소 경유 요청 | 실제 반영 결과 확인 | 충전소 제안만 표시, 목적지 단독 전달 |

FusedLocation 활성화 시 마지막 위치는 새 측정값을 보장하지 않고 null일 수 있다. 센서 시각과 앱 수신 시각을 분리하고 시간 단위를 확인한 뒤 5분 이상 지난 위치를 오래된 값으로 표시한다. 측정 시각을 해석할 수 없으면 수신 시각만으로 최신이라고 판단하지 않는다. 5분은 팀 구현 기본값이다. [FusedLocation 소개](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/FusedLocation/intro)

NaviHelper는 기본 내비 서비스에 목적지·경유지·화면 표시 등을 요청하고 이벤트를 받는다. 요청 접수와 실제 경로 안내를 구분하며 앱 자체 내비 엔진을 만들지 않는다. [NaviHelper 소개](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/intro)

### 수면 준비 기본값과 완료 판정

아래 제어 절차는 조건부 활성화 경로다. 기본 P0의 수면 안내만 제공할 때는 제어 요청·자동 적용·자동 복원으로 표현하지 않는다.

- 제안값은 공조 21°C, 조절 가능하고 단위가 검증된 경우 풍량 1단, 지원 시 실내등/앰비언트 끄기다. 차종별 유효 범위 밖이면 요청하지 않는다. 차박 적정값으로 보장하지 않는다.
- 내기순환 고정, 시트 이동, 열선, 창문, V2L은 P0 자동 제어 대상에서 제외한다.
- 수면 안내 화면은 플랫폼이 허용하는 정차형 조작 상태 + 도착 확인으로 진입한다. 직접 제어는 여기에 신뢰 가능한 주차 상태 확인을 추가한다. 자동 도착 이벤트를 얻지 못하면 허용된 화면에서 '도착했어요'로 확인하되 이 입력을 주차 상태 증거로 쓰지 않는다.
- 원래 값을 읽고 로컬에 저장한 항목만 요청한다. 적용 전에 항목별 원래 값→요청 값을 보여준다.
- `대기 → 요청 중 → 요청 성공 → 차량 확인됨` 또는 `실패/미지원/확인 불가`로 상태를 나눈다. 콜백 성공 후 재조회가 다르면 차량 확인 완료로 표시하지 않는다.
- 읽기 요청은 10초, 제어 결과 확인은 15초를 팀 기본 타임아웃으로 둔다. SDK가 정한 계약이 있으면 그것을 우선한다. 타임아웃 뒤 자동 제어 재시도는 하지 않는다.
- 늦은 콜백과 재시도는 요청 ID로 구분한다. 주행 전환 시 새 제어를 차단하되 이미 보낸 요청을 취소한 것처럼 표시하지 않고 결과를 추적한다.
- 재실행 시 미완료 제어 기록을 읽어 실제 상태를 조회하며 같은 요청을 자동 재전송하지 않는다.
- P0 종료에서는 변경 항목과 원래 값을 보여주고 사용자가 차량 기본 설정에서 복원하도록 안내한다. P1 자동 복원을 추가하면 현재 값이 앱의 마지막 적용값과 다를 때 덮어쓰지 않고 확인을 받는다.

## 13. SDK 개발자 문서 반영: 구현 계약과 추가 검수

### 13.1 착수 관문과 의존성

착수 순서를 `My Project 기능 상태 → 의존성/최소 빌드 → API 시그니처·단위 → 런타임 권한·Capability → 실제 호출`로 고정한다. 콘솔 접근이 없거나 상태가 미확인이면 조건부 기능을 활성화하지 않는다. APK가 설치된다는 사실만으로 SDK 승인·서비스 연결이 확인된 것은 아니다.

첨부 가이드에 제시된 Maven 저장소는 `https://nexus-playground.pleos.ai/repository/maven-releases/`, 최초 의존성은 `ai.pleos.playground:Vehicle:2.3.2`, `ai.pleos.playground:NaviHelper:3.0.5`다. 다운로드와 최소 빌드는 아직 실행하지 않았다. 버전·좌표·AAR 내 계약을 확인해 검증표에 기록한다. FusedLocation·음성·제어 기능은 가이드 예제를 그대로 전부 추가하지 않는다.

### 13.2 최소 권한 대응

| 기능 | 선언 후보 | 활성화 조건 |
| --- | --- | --- |
| SOC 조회 | `pleos.car.permission.CAR_ENERGY` | 실제 getter의 요구 권한과 승인 범위 대조 |
| 목적지·경유지 요청 | `pleos.car.permission.NAVI_ROUTE_SEARCH` | 호출 기능과 일치 |
| 목적지·내비 정보 조회 | `pleos.car.permission.NAVI_ROUTE` | 정보 조회를 구현할 때 |
| 내비 화면 표시 요청 | `pleos.car.permission.NAVI_CUSTOM_MAP` | 해당 API를 구현할 때; 경로 요청 권한과 별개 |
| 위치 자동 조회 | `pleos.car.permission.FUSED_LOCATION` | 프로젝트 사용 가능 상태·지원 여부 확인 후 |
| 공조·조명 조회 | `CAR_CLIMATE`, `CAR_LIGHTS` 계열 | 정확한 전체 문자열·함수별 요구 권한 확인 |

내비 권한은 공식 대응표로 재확인했다. Vehicle 권한 후보는 첨부 가이드와 설치 AAR의 `@RequiresPermission`을 대조하는 대상이다. Door/Window·TTS·STT는 기본 제출 구성에 선언하지 않는다. [NaviHelper 권한](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/declaring-permissions)

### 13.3 SOC·Capability·제어 계약

- SOC의 후보 식별자는 `checkEvBatteryStateOfChargeCapabilities`, `getEvBatteryStateOfCharge`, `registerEvBatteryStateOfCharge`, `unregisterEvBatteryStateOfCharge`다. 첨부 가이드의 **API 목록 확인** 수준이며, 반환 타입·단위·리스너 전체 시그니처가 검증됐다는 뜻이 아니다.
- 기능별 `CapabilityConfig` 접근 수준을 확인한다. 읽기는 READ/READ_WRITE, 쓰기는 WRITE/READ_WRITE일 때만 후보가 된다. 우리 앱의 수면 제어는 변경 전 읽기·변경 후 재조회도 필요하므로 WRITE만으로 활성화하지 않는다.
- 영역·최소/최대 범위를 실제 응답으로 구성한다. 풍량 capability는 목록이 아닌 `AreaBounds<Int>` 기반으로 처리하고, 1단이 허용 범위에 있는지 확인한다. 범위 밖 값을 조용히 보정해 요청하지 않는다.
- 목표 온도와 실내 측정 온도, 조명 스위치와 실제 조명 상태를 구분한다. 같은 의미의 설정값/조회값끼리 비교한다. 온도 요청 결과를 실내 측정 온도와 비교해 성공 판정하지 않는다.
- 설정 프리셋은 앱이 조합한 개별 요청이다. 원자적 일괄 성공·일괄 복원을 가정하지 않는다. 원래 값과 결과를 항목·영역별로 저장한다.
- 지원·승인·연결 상태를 각각 저장하고 재연결 시 재확인한다. SOC 실패를 ICE로 판정하거나 SOC 제공만으로 BEV로 판정하지 않는다.

접근 수준과 범위 모델은 [Capability 공식 가이드](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/Vehicle/check-capability)를 기준으로 한다. 첨부 자료의 도메인 식별자 전체는 구현 전 AAR 확인 항목으로 남긴다.

### 13.4 내비게이션 호출·좌표·이벤트

1. `initialize` 연결 완료 후 동일 리스너 인스턴스를 등록한다. 최신 버전의 실패 콜백도 처리한다.
2. 사용자가 확인한 차량 진입구를 목적지로 사용한다. 진입구가 미확인이면 이를 알리고 좌표 확인 후 요청하며 대표 좌표가 진입구라고 가정하지 않는다.
3. 3.0.5 모델은 위도·경도 순서다. Kotlin named argument를 지원하는 선언에서는 이름을 쓰고, 지원하지 않으면 확인한 생성자를 한 어댑터에 감싼다. 위도 ±90/경도 ±180뿐 아니라 서울·수도권 대상 위치와도 대조한다.
4. 장소 자체 ID를 Pleos `poiId`로 복사하지 않는다. 외부 좌표만 가진 `RouteInfo`의 필수 필드·POI 미지정 계약을 AAR/샘플로 확인한 후 구성한다.
5. `requestRoute(RouteInfo)` 또는 `requestRouteWithWaypoints(RouteWithWaypointsRequest)`를 호출한다. 경유지 전달 불가 시 목적지 단독 요청 여부를 사용자에게 보여준다.
6. `onRouteStarted`는 탐색 시작, `onRoutingCompleted`는 탐색 완료다. 탐색 완료를 차량 출발·목적지 도착·안내 활성화와 동일시하지 않는다. 안내 상태는 `onNavigationStatus` 및 실제 내비 화면으로 별도 확인한다.
7. `getDestinationInfo()`의 결과는 `onDestinationInfo()`에서 받는다. `remainDistance`, `remainTime`은 단위를 확인한 후 표시한다.
8. `onDestinationArrived`는 도착 신호일 뿐 주차 증거가 아니다. `requestNavigationScreen` 실패도 경로 요청 실패와 별도로 처리한다.
9. `cancelRoute()`는 사용자가 취소할 때만 호출한다. 화면을 닫거나 리스너를 해제할 때 자동으로 기본 내비 경로를 취소하지 않는다.

SDK가 앱의 요청 ID를 되돌려 준다고 가정하지 않는다. 앱 내부 generation/요청 상태와 목적지 조회로 오래된 이벤트를 배제하고, 요청 중 중복 탭을 막는다. 필요한 이벤트가 실제 환경에서 제공되지 않으면 추정 완료 대신 확인 불가를 표시한다. [이벤트 가이드](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/event-listeners)

좌표 순서, `NavigationStatus`, `remainDistance/remainTime`, `onRoutingCompleted` 변경은 [공식 릴리스 노트](https://document.pleos.ai/docs/pleos-only/release-note/sdk-release-note)로 재확인했다. 오래된 `onRouteEnded`나 제거된 `VehicleSpeedListener`를 신규 구현에 사용하지 않는다.

### 13.5 주행 제한·수명·오류

- 플랫폼 UX 제한과 주차 상태를 분리한다. UX 제한 해제, GPS 속도 0, 브레이크 신호, 내비 도착만으로 주차 완료를 확정하지 않는다. UX 제한이 불명인 경우 상세 조작을 잠그고, 주차 상태가 불명인 경우 직접 제어를 잠근다. `CarUxRestrictionsManager`는 Pleos에서 접근 가능 여부를 확인할 후보이지 검증된 연결이 아니다.
- Vehicle 연결 후 도메인 객체를 획득한다. 필요한 콜백이 끝나기 전에 release하지 않고, 종료 시 등록한 인스턴스로 구독 해제 후 리소스를 정리한다.
- 콜백 스레드에서 Compose 상태를 직접 변경하지 않는다. 어댑터→상태 저장 계층→UI 수집으로 전달하고, 화면 재생성·내비 복귀에서 중복 구독을 방지한다.
- 앱 수신 시각과 센서 시각을 분리한다. SOC는 초기 조회/갱신 성공값만 유효 판단에 쓰고, 연결 종료·재진입·오류 뒤 이전 값을 stale로 표시하여 재조회한다. 제출 데모의 SOC 최대 유효 시간은 팀 기본값 60초로 두며 해당 시간은 SDK 계약이 아니다.
- Vehicle `onFailed(Exception)`에서 `VehicleException`인 경우에만 errorCode를 읽고 일반 Exception도 처리한다. UI에는 미지원, 권한 부족, 연결 끊김, 값 없음, 타입 오류, 주행 제한을 구분한다.
- 미지원 속성/영역은 해당 기능/영역을 제외하고, 권한 오류는 반복 재시도하지 않는다. 서비스 연결·일시 오류의 읽기는 재초기화 후 1회만 자동 재시도하고 이후 수동 재시도로 전환한다. 쓰기는 자동 재전송하지 않는다.
- `ERROR_EMPTY_RESULT`를 0·닫힘·준비 완료로 바꾸지 않는다. `ERROR_DRIVING_RESTRICTED`는 조작을 중지하고 입력 상태를 보존한다. `ERROR_NOT_SUPPORTED_VALUE_TYPE`는 인자·변환 오류로 기록한다. [Vehicle 오류 가이드](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/Vehicle/vehicle-error-code)
- Virtual Console의 테스트 카드만으로 앱 API 공개·권한·실차 지원을 판단하지 않는다. 데모 토글은 실제 제어를 우회하지 못하도록 Fake Adapter에만 연결한다.

### 13.6 추가 테스트와 인수 증거

| 사례 | 기대 결과 |
| --- | --- |
| FusedLocation/Vehicle Control 준비 중 | 기본 P0 실행 가능, 조건부 호출 없음, 자동 조회/직접 적용 표현 없음 |
| Capability NONE/READ/WRITE/READ_WRITE | 실제 접근 수준과 우리 앱의 읽기·제어 조건 모두 충족할 때만 실행 |
| SOC raw 스케일·단위 미확인 | 충전 규칙 투입 차단; 0%·35% 임계값으로 오판하지 않음 |
| 권한 부족/미지원/연결 해제 | 서로 다른 상태·대안, 자동 완료 없음 |
| 좌표 역전·범위는 맞지만 지역 불일치 | 목적지 요청 전 검증·사용자 확인 |
| 탐색 완료 이벤트만 수신 | 탐색 완료만 표시, 안내 활성/도착은 별도 판정 |
| UX 제한 해제지만 주차 상태 불명 | 허용 UI만 제공, 직접 제어 비활성 |
| 오래된 센서값을 방금 수신 | 수신 시각만으로 최신 판정하지 않음 |
| 재연결·내비 복귀·화면 재생성 | 리스너 중복 없음, Capability 재확인, 이전 요청 자동 반복 없음 |
| 사용자 설정 변경·부분 성공 | 항목별 결과 보존, 사용자 변경 덮어쓰기 없음 |

검증표에는 `기능/SDK 버전/식별자/확인 수준/시그니처/단위/영역/권한/프로젝트 상태/에뮬레이터 결과/대체 동작`을 기록한다. 시그니처 미확인·프로젝트 상태 미확인은 빈칸 대신 미확인으로 남긴다. 이 개정에서 AAR 다운로드·My Project 열람·빌드·에뮬레이터 테스트는 수행하지 않았다.
