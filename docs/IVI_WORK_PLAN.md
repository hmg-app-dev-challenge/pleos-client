# 차Park v2.1.1 개발 실행 계획

2026-11-13 · 기준: [제품 기획 v2.1.1](PRODUCT_SPEC_V2_1.md) · Android 1명 / 서버 1명 기준 작업 분담.

기준 원문은 [Ver 2.1.1](reference/CHAPARK_PROPOSAL_V2_1_1.md)이며 [변경 대조](V2_1_1_CHANGE_REVIEW.md)에 실질 변경과 유지 요구를 구분했다. 문서 버전 갱신은 앱 버전·승인·구현 완료를 뜻하지 않는다. Android 1명/서버 1명은 역할 배분이며 별도 에이전트 실행 지시가 아니다. 마감일을 추정하지 않고 의존성과 인수 조건으로 순서를 관리한다.

최신 단계별 근거와 커밋: [실행 기록](V2_1_1_EXECUTION.md), [최종 인수 범위](V2_1_1_ACCEPTANCE.md). 아래 기반 표는 개정 전 출발점이며 현재 상태는 단계별 표를 따른다.

## 실행 순서와 분기

1. **P01 + B1/B2/B3 마무리:** 문구를 작은 여행 중심으로 조정하고 SOC 연속 변경·오류·미지원 UI·수동 입력·실제 UX 전환을 검증한다. 기존 A3/A4의 날짜와 체크 관문 회귀를 함께 실행한다.
2. **C1/C2:** 장소 유형/풍경/이용 조건/조망/충전소의 출처 계약을 만든 뒤 실제 후보를 검토한다. 조사되지 않은 조건을 대표 시나리오에 맞춰 허용으로 바꾸지 않는다. 필수 조건 미확인 후보와 제외 이유를 표시한다.
3. **D2/D3/D4:** 확인된 충전소로 순서 있는 경유 요청과 실제 안내를 검증한다. 목적지와 경유지를 모두 대조한다. 시간 계약 미확보는 권장 안내로 처리할 수 있으나 경유 요구 자체를 제거하지 않는다.
4. **E1/E2/E3:** 공식 계산식과 기준값·허용 오차를 먼저 대조하고 시각/방위를 기록한다. 조망 근거가 있으면 방향 조합, 없으면 계산 정보만 표시한다. 시간 배경은 실제 풍경/기상 재현으로 표현하지 않는다.
5. **F1/F2 + A2:** 장소 선택부터 철수까지의 실제/계산 사건 및 당시 근거를 snapshot으로 저장하고 한 장의 기억 카드로 구성한다. 일반 미확인 조건과 명시적 누락 준비물을 구분해 다음 여행으로 연결한다. 완료 기록은 불변이며 내용 수정이 필요하면 revision 계약을 먼저 정한다.
6. **G1/G2:** 현재 로컬 기록 서버를 장소/규칙/계획 계약으로 확장한다. 로컬 캐시·계획 revision·충돌 해소·삭제 전파와 중단 후 재전송을 검증한다. 외부 배포나 계정 연동은 자동으로 포함하지 않는다.
7. **H1/H2:** 2.1.1 대표 흐름·예외·기존 UI 회귀와 release 새 설치를 통과한 후 제출 산출물을 준비한다. 기존 debug APK를 이름만 바꿔 release로 취급하지 않는다. P02의 시장 근거는 제출 전에 검증한다.

| X2 | 에너지/전력 데이터 검증 | X1 허용 범위 확인 | 두 속성의 config/status/value/time, 단위·부호·갱신·오류·해제, 실제 표본 수집과 유효성 판정 | 현재 직접 값 미수신 |
| X3 | 목표 잔량까지 시간 추정 실험 | X2 + 목표 SOC/에너지 변환 근거 | 최근 소비 표본 선택, 안정성·오차 기준 사전 정의, 계산 버전/시각/표본/추정 출처 표시, 부적합 상태에서 숫자 숨김 | 설계 검토 대기 |

X3 설계 시 확인할 항목: 유효한 현재 가용 에너지, 사용자 목표 SOC에 대응하는 에너지, 최근 소비 추세, 충전/방전 부호, 0 근처 소비, 급변 부하, 오래된 표본, 목표 이미 도달, 앱 종료 후 갱신 중단. 실제 표본·모델 검증 없이 Wh/mW 원시값을 임의로 나눠 제품 시간으로 노출하지 않는다. 특정 공조 설정의 보장 시간·도착 SOC·귀가 가능 판단으로 확장하지 않는다.

## 공통 모델과 저장 설계

아래 이름은 신규 구현 제안이며 현재 존재하는 클래스라고 보지 않는다.

- `VehicleReading`: 값, 원시값, 정규화 단위, capability, 상태, 출처(vehicle/manual/emulator/example), 앱 수신 시각, 제공되는 경우 센서 시각. 출처와 지원 상태를 별도로 관리한다.
- `TripPlan`: 안정적 여행 ID, 여행 날짜·시간대, 인원, 취사, 종료 시각, 사용자 SOC 확인 기준, 장소·경유지 선택, 규칙 버전. 기존 반려동물·침낭 조건 유지.
- `PlaceEvidence`: 장소 유형, 풍경 유형, 좋은 순간을 분리하고 속성별 값·근거 URL·확인일·확인 주체, 대표 좌표/차량 진입구, 주차/숙박/화장실/취사, 풍경 태그·조망 방위. 충전소는 위치 외 커넥터·이용 조건·정보 출처를 갖고 실시간 가용성 미확인은 별도 표시.
- `PreparationItem`: stable ID, 의미/규칙 버전, 수량, 출발 전/짐/현장 단계, 사용자 확인 내용·시각. 현장 항목을 일괄 출발 관문에 넣지 않는다.
- `NavigationAttempt`: 목적지·순서 있는 경유지, generation, 요청/탐색/안내/실패 상태와 실제 SDK 관측, 시간 정보의 단위·측정 시각.
- `SolarEvent`: 장소·날짜·시간대, 계산 시각·방위·계산 버전. 장소 조사와 조합한 안내는 근거를 함께 참조.
- `TripRecord`: 계획·장소 근거·규칙의 당시 스냅샷, 실제 사건 및 계산 사건의 타입별 타임라인, 출발·철수 SOC, 체크·충전 판단·누락 준비물. 안전 점수나 보증으로 변환하지 않는다.
- `EnergyReading` / `UsageEstimate` (확장 제안): API/권한/차종 지원 근거, 에너지·전력 원시값과 정규화 단위·부호·상태·시각, 목표 잔량과 에너지 환산 근거, 표본 구간·계산 버전·불확실성·표시 가능 여부. X1~X3 이전 제품 저장·전송 대상이 아님.
- `SyncOperation`: 여행/기록 ID, 로컬 revision, idempotency key, 대기/전송/실패 상태. 서버 갱신이 사용자 체크나 기록을 조용히 덮어쓰지 않도록 충돌 정책 적용.

활성 여행과 archive·삭제 목록은 현재 DataStore 스키마 5를 사용한다. 별도 Room/outbox는 아직 없다. 기록 규모·캐시·revision 확장 시 Room 도입 여부를 A1/G1에서 결정한다. 다음 스키마에서도 1~5의 기존 여행을 보존하고 기본값 새 여행으로 덮어쓰지 않는다. 과거 데이터에 없던 시각·출처·배터리는 null/미수집으로 보존한다. 폰과 공유 모델 변경 시 폰의 상태 복원·규칙 회귀를 확인한다.

## 서버 계약 초안

| 계약 | 최소 데이터와 동작 |
| --- | --- |
| 장소·충전소 조회 | 버전/갱신 시각, 필터, 속성별 출처·확인일, 풍경·조망, 빈 결과 원인, 좌표 종류 |
| 준비 규칙 조회 | schema/rule version, 적용 조건, 단계·수량, 로컬 기본 규칙과 호환 여부 |
| 계획 저장·조회 | 여행 ID·revision 기반 변경, 재전송 중복 방지, 충돌 응답 |
| 기록 저장·조회 | 사건/읽기 출처를 보존하는 snapshot, idempotency, 로컬 완료와 서버 저장 상태 분리 |

현재 구현은 단일 사용자 loopback 서버, Bearer 토큰, 불변 기록·계획 revision, 409 충돌·410 삭제 보존이다. IVI는 실행 중 15초 주기로 동기화하고 기록을 추가 병합한다. 장소/규칙 버전 캐시는 새 여행에서 적용한다. 계획 조건은 사용자 확인 후 새 여행으로 가져오며 진행 상태·현장 확인을 자동 복원하지 않는다. release 로컬 서버 연결은 꺼져 있다. [실행/API](../server/README.md)를 기준으로 확장한다. 인증·장치 식별·접근 범위·보관/삭제 정책은 G1의 필수 설계 항목이다. 계정 연동이 확장이라는 이유로 여행 기록 API를 공개 쓰기/읽기로 제공하지 않는다. 서버 제공자·새 외부 서비스 생성은 아직 선택하지 않는다. QR 공유는 접근 범위·만료·공유 해제를 포함한 확장 작업으로 분리한다.

## SDK 및 디자인 확인 관문

첨부 기획서의 API 목록은 구현 요구와 검증 후보로 취급한다. `requestRouteWithWaypoints`, `RequestWaypointInfo`, `onTripInfo`, Brake/DrivingMode 신호 및 각 권한은 고정된 AAR·공식 문서·런타임으로 확인한 계약만 코드에 넣는다. SDK 제공 상태는 My Project에서 재확인한다. 지원하지 않는 기능을 코드에서 추정해 호출하지 않는다.

NaviHelper 단일 목적지는 이미 검증했다. 현재 에뮬레이터에서는 배경 지도 타일이 회색이며 자동 이동 재생은 검증되지 않았다. 원인 조사와 제공 내비 앱 환경 확인을 H1의 통합 이슈로 남긴다. 실제 도착 이벤트 분기는 구현돼 있으나 기존 전체 흐름 검증의 도착은 사용자 확인이다.

기존 Pleos Figma 시스템의 색상·Asta Sans·타입·버튼·선택·팝업을 재사용한다. 기록 카드·풍경 태그·태양 배경·따뜻한 밤 테마는 앱 고유 확장이므로 원본 컴포넌트라고 주장하지 않는다. 구현 시 Figma 원본을 다시 대조하고 상태별 매핑과 대비·가로/좁은 창 검수를 남긴다. 출처 라벨은 표시하되 개발용 조작·시연 배너는 사용자 화면에 넣지 않는다.

## 완료 보고 기준

핵심 요구 R01~R13에 대해 구현 경로·테스트·화면 증거를 연결한다. 조건부 SDK 기능은 확인한 가용성과 대체 흐름을 기록한다. 폰·QR·직접 제어·음성은 핵심 완료의 필수 조건에 넣지 않는다. release APK·영상·저장소 정보는 실제 산출물로만 채우고, 기획 버전 2.1.1을 APK 버전 또는 배포 완료로 표시하지 않는다.
